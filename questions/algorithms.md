# Алгоритмы и структуры данных: теория для собеседования

На coding-интервью кроме кода спрашивают: «какая сложность?», «а если данных в 1000 раз
больше?», «почему не другая структура?». Ответ на эти вопросы так же важен, как
работающий код.

## Как решать задачу на интервью (порядок важен)

1. **Уточни условие.** Размер входа? Бывают ли пустые входы, дубликаты, отрицательные числа?
   Можно ли менять вход? Что вернуть, если ответа нет?
2. **Разбери пример руками** и придумай свой, в том числе краевой.
3. **Назови наивное решение и его сложность.** Даже O(n²) лучше, чем молчание.
4. **Ищи узкое место:** что повторяется? Что можно запомнить (хеш-таблица)? Отсортировать?
5. **Проговори план** и сложность ДО кода, получи согласие интервьюера.
6. **Пиши код** с понятными именами, проговаривая, что делаешь.
7. **Проверь** на примере и краевых случаях, пройди код глазами построчно.
8. **Назови итоговую сложность** по времени и памяти.

## Вопросы

**1. Что такое O-большое? Почему отбрасывают константы?**
<details><summary>Ответ</summary>

Верхняя оценка роста числа операций (или памяти) при росте входа n. Константы отбрасывают, потому что при больших n форма роста важнее множителя: O(n) с константой 100 обгонит O(n²) уже при n > 100. На практике константы важны (кеш процессора, Python против C), но сравнение алгоритмов начинают с асимптотики.
</details>

**2. Ограничение n ≤ 10⁵. Какая сложность нужна?**
<details><summary>Ответ</summary>

Python выполняет порядка 10⁷ простых операций в секунду. O(n²) = 10¹⁰ — слишком долго. Нужно O(n log n) или O(n). Ориентиры: n ≤ 20 — перебор O(2ⁿ); n ≤ 10³ — O(n²); n ≤ 10⁵–10⁶ — O(n log n); больше — O(n) или O(log n).
</details>

**3. Что такое амортизированная сложность? Пример.**
<details><summary>Ответ</summary>

Средняя стоимость операции на длинной серии, когда редкие операции дорогие. `list.append`: иногда массив копируется целиком (O(n)), но ёмкость растёт в разы, поэтому n вставок стоят O(n) суммарно, то есть O(1) в среднем. То же у расширения хеш-таблицы и очереди на двух стеках.
</details>

**4. Массив против связного списка.**
<details><summary>Ответ</summary>

Массив: доступ по индексу O(1), вставка в середину O(n), данные лежат подряд — дружит с кешем процессора. Связный список: доступ O(n), вставка/удаление при известном узле O(1), но лишняя память на указатели и промахи кеша. На практике массив почти всегда быстрее; список нужен, когда много вставок/удалений в середине по ссылке (LRU-кеш).
</details>

**5. Хеш-таблица: как работает, что такое коллизии, load factor?**
<details><summary>Ответ</summary>

Ключ -> hash -> номер ячейки. Коллизия — два ключа в одной ячейке; решается цепочками (список в ячейке) или открытой адресацией (поиск следующей свободной). Load factor = элементов / ячеек; при превышении порога (0.66–0.75) таблицу увеличивают и перекладывают ключи. Поиск O(1) в среднем, O(n) в худшем.
</details>

**6. Когда стек, когда очередь, когда куча?**
<details><summary>Ответ</summary>

Стек (LIFO): вложенность, отмена действий, DFS, монотонный стек «следующий больший». Очередь (FIFO): BFS, обработка в порядке поступления, буферы. Куча: нужен минимум/максимум с быстрыми вставками — top-k, слияние k потоков, Дейкстра, планировщики задач.
</details>

**7. Почему heapify работает за O(n), а не O(n log n)?**
<details><summary>Ответ</summary>

Просеиваем вниз узлы снизу вверх. Половина узлов — листья (0 работы), четверть — на высоте 1 (1 шаг), восьмая — на высоте 2... Сумма n/4·1 + n/8·2 + n/16·3 + ... = O(n). n вставок по одному стоили бы O(n log n).
</details>

**8. BST против хеш-таблицы. Что такое сбалансированное дерево?**
<details><summary>Ответ</summary>

Хеш-таблица быстрее для точного поиска (O(1)), но не хранит порядок. BST даёт упорядоченный обход, min/max, поиск по диапазону, «ближайший больший» — за O(h). Без балансировки h может стать n (вставка по возрастанию). Сбалансированные деревья (красно-чёрное, AVL, B-дерево в БД) гарантируют h = O(log n).
</details>

**9. BFS против DFS.**
<details><summary>Ответ</summary>

BFS (очередь) обходит по уровням и находит кратчайший путь в невзвешенном графе; памяти нужно O(ширина). DFS (стек/рекурсия) уходит вглубь: компоненты связности, поиск циклов, топологическая сортировка, перебор; памяти O(глубина). Рекурсивный DFS в Python упирается в лимит глубины 1000 — на больших графах используй явный стек.
</details>

**10. Дейкстра: идея, сложность, ограничения.**
<details><summary>Ответ</summary>

Жадно достаём из кучи вершину с наименьшим известным расстоянием — оно уже окончательное — и релаксируем рёбра. С кучей O((V + E) log V). Не работает с отрицательными весами (тогда Беллман — Форд). Для невзвешенного графа хватает BFS.
</details>

**11. Динамическое программирование против жадного алгоритма.**
<details><summary>Ответ</summary>

Жадный делает локально лучший выбор и не пересматривает его — быстро, но верно только для задач с особой структурой (сдача монетами 1/5/10/25 — да, 1/3/4 — нет: для 6 жадный даст 4+1+1, оптимум 3+3). DP перебирает все варианты через подзадачи и запоминает их ответы, поэтому корректно в общем случае ценой времени/памяти.
</details>

**12. Мемоизация против табуляции.**
<details><summary>Ответ</summary>

Мемоизация (сверху вниз): рекурсия + кеш (`@functools.cache`), считает только нужные состояния, проще написать, но есть риск переполнения стека. Табуляция (снизу вверх): цикл по таблице в правильном порядке, нет рекурсии, часто можно хранить только последнюю строку (O(n) памяти вместо O(n·m)).
</details>

**13. Устойчивая сортировка. Какая сортировка в Python и её сложность?**
<details><summary>Ответ</summary>

Устойчивая — равные элементы сохраняют исходный порядок (важно при сортировке по нескольким ключам по очереди). В Python — Timsort (с 3.11 — Powersort-вариант слияния): устойчивая, O(n log n) в худшем, O(n) на почти отсортированных данных. Нижняя граница для сортировок сравнениями — Ω(n log n); быстрее можно только без сравнений (counting / radix / bucket sort) при ограниченных значениях.
</details>

**14. Как найти ошибку в решении, если примеры проходят?**
<details><summary>Ответ</summary>

Стресс-тест: напиши заведомо правильное наивное решение и сравни на тысячах случайных маленьких входов. Первый расхождение — готовый минимальный пример ошибки. Так устроены многие тесты в `tests/` этого репозитория.
</details>
