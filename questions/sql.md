# SQL: вопросы с собеседований

ML-инженер постоянно пишет SQL: собирает выборки, считает признаки и метрики.
Подробная практика будет в проекте `databases-lab`; здесь — теория, которую спрашивают.

**1. Порядок выполнения SELECT-запроса.**
<details><summary>Ответ</summary>

`FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT (оконные функции здесь) -> DISTINCT -> ORDER BY -> LIMIT`. Поэтому в `WHERE` нельзя использовать алиас из `SELECT` и агрегаты, а в `ORDER BY` можно.
</details>

**2. `WHERE` против `HAVING`.**
<details><summary>Ответ</summary>

`WHERE` фильтрует строки до группировки, `HAVING` — группы после агрегации (`HAVING COUNT(*) > 5`). Всё, что можно отфильтровать в `WHERE`, лучше фильтровать там: меньше данных уходит в группировку.
</details>

**3. Виды JOIN. Что вернёт LEFT JOIN, если справа несколько совпадений?**
<details><summary>Ответ</summary>

`INNER` — только совпавшие пары; `LEFT` — все строки слева, справа `NULL` при отсутствии пары; `RIGHT` — наоборот; `FULL OUTER` — все с обеих сторон; `CROSS` — декартово произведение. При нескольких совпадениях строка слева размножается — частая причина «раздувания» данных и неверных сумм после JOIN.
</details>

**4. Почему `WHERE col = NULL` ничего не находит? Как работает `COUNT(col)` с NULL?**
<details><summary>Ответ</summary>

Любое сравнение с `NULL` даёт `UNKNOWN`, а не `TRUE`. Нужно `IS NULL` / `IS NOT NULL`. `COUNT(*)` считает строки, `COUNT(col)` — только не-NULL значения; `AVG` тоже игнорирует NULL. Ловушка: `NOT IN (подзапрос с NULL)` возвращает пустой результат.
</details>

**5. Оконные функции: чем отличаются от GROUP BY? `ROW_NUMBER`, `RANK`, `DENSE_RANK`.**
<details><summary>Ответ</summary>

`GROUP BY` схлопывает строки в одну на группу; оконная функция (`... OVER (PARTITION BY ... ORDER BY ...)`) считает по группе, но сохраняет все строки. `ROW_NUMBER` — 1,2,3,4 без повторов; `RANK` — 1,2,2,4 (пропуски после равных); `DENSE_RANK` — 1,2,2,3. Типичные задачи: топ-N в каждой группе, скользящее среднее, `LAG`/`LEAD` для разницы с предыдущей строкой, накопительная сумма.
</details>

**6. Напиши запрос: второй по величине оклад / топ-3 товара в каждой категории.**
<details><summary>Ответ</summary>

```sql
-- топ-3 в каждой категории
SELECT *
FROM (
  SELECT p.*, ROW_NUMBER() OVER (PARTITION BY category ORDER BY revenue DESC) AS rn
  FROM products p
) t
WHERE rn <= 3;

-- второй по величине оклад (без повторов)
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
```
</details>

**7. Что такое индекс? Когда он не помогает или вредит?**
<details><summary>Ответ</summary>

Чаще всего B-дерево по значениям столбца: поиск O(log n) вместо полного сканирования. Не помогает: функция над столбцом в условии (`WHERE lower(email) = ...` без функционального индекса), `LIKE '%abc'`, низкая селективность (запрос всё равно вернёт половину таблицы). Вредит: замедляет вставки и обновления, занимает место. Составной индекс `(a, b)` работает для условий по `a` и по `a, b`, но не по одному `b`. Проверка: `EXPLAIN ANALYZE`.
</details>

**8. Что такое транзакция и ACID?**
<details><summary>Ответ</summary>

Группа операций, выполняемая как единое целое. Atomicity — всё или ничего; Consistency — переход между корректными состояниями; Isolation — параллельные транзакции не мешают друг другу (в рамках уровня изоляции); Durability — подтверждённое не потеряется при сбое.
</details>

**9. Уровни изоляции и аномалии.**
<details><summary>Ответ</summary>

Read uncommitted (видны чужие незафиксированные изменения — dirty read), read committed (по умолчанию в PostgreSQL; возможны non-repeatable read), repeatable read (возможны phantom reads по стандарту; в PostgreSQL фантомов нет), serializable (как будто транзакции шли по очереди). Выше уровень — меньше аномалий, больше блокировок и откатов.
</details>

**10. Нормализация и денормализация. Когда денормализуют?**
<details><summary>Ответ</summary>

Нормализация убирает дублирование (каждый факт хранится один раз): проще обновлять, меньше аномалий. Денормализация (хранить заранее соединённые/агрегированные данные) ускоряет чтение ценой дублирования — для аналитики, витрин признаков, нагруженных чтением сервисов.
</details>

**11. SQL против NoSQL. OLTP против OLAP.**
<details><summary>Ответ</summary>

Реляционные БД: схема, JOIN, транзакции — для данных со связями и требованиями к целостности. NoSQL: документные (MongoDB), key-value (Redis), колоночные (Cassandra), графовые — гибкая схема, горизонтальное масштабирование, конкретные паттерны доступа. OLTP — много мелких транзакций (заказы), строковое хранение. OLAP — тяжёлые аналитические запросы по большим объёмам (ClickHouse, BigQuery), колоночное хранение.
</details>

**12. `UNION` против `UNION ALL`; `DELETE` против `TRUNCATE`.**
<details><summary>Ответ</summary>

`UNION` убирает дубликаты (дороже: сортировка или хеширование), `UNION ALL` — нет. `DELETE` удаляет строки по условию, пишет в журнал, срабатывают триггеры; `TRUNCATE` очищает таблицу целиком быстро, без построчного удаления.
</details>
